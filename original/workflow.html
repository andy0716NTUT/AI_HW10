Process / Verification

Wiki → HTML 簡報：Graph 與檢查

Wiki　·　簡報

先討論、後生成（需求定義）

選題：AI Agent。對象：完全沒有相關背景的學生。問題範圍：定義、組成、工具迴圈、Graph、模式與安全。輸出限制：10 頁、繁體中文、不假設讀者有程式背景。這些設計決策先固定，再整理 Wiki 與生成簡報。

Graph 流程

START → 定義主題與教學目標
      → 取得 5 篇技術來源
      → 來源檢查 (連結、內容相關性)
           ├─ 失敗 → 重新查來源 (上限 2 次)
           └─ 通過 → 摘要與知識條目化
                     → Wiki 來源映射檢查
                          ├─ 失敗 → 修正摘要 / 引用
                          └─ 通過 → 依課程順序檢索 Wiki
                                    → 產生 HTML 投影片
                                    → 自動檢查
                                         ├─ 失敗 → 修正 HTML / 映射
                                         └─ 通過 → END

會重複：資料來源不適切時重新查詢；條目缺引用時修摘要；投影片無法導覽、缺標註時修 HTML。檢查前移：不等投影片完成才核對來源，先在 Wiki 資料結構建立 source ID 與 entry ID 對應。

本次實際執行與可驗證紀錄

  • 資料來源：5 筆外部文件，記錄 URL 與整理要點（S01–S05）。
  • Wiki：6 個條目（W01–W06），每個條目具有至少一個來源 ID。
  • 簡報：10 張，逐頁記錄所引用的 Wiki 條目 ID。
  • 本機靜態檢查：請查看 validation.json；該檔記錄可程式驗證的結果。
  • 限制：本次沒有實作真正的 LLM 自動重試執行器，也沒有第三方 LLM Wiki 平台的 ingest API 紀錄；Graph 是可追蹤的設計與本次人工輔助流程，而不是已自動執行的 LangGraph 工作流。

反思（依本次生成檢查；非虛構多輪統計）

最容易出錯的節點：「Wiki 摘要 → 投影片」之間的來源對應。整理內容時容易把多篇概念混合，最後只留一個模糊參考來源。

檢查往前移：在 Wiki 建條目時強制填入 sources[]，在投影片生成時強制填入 Wiki IDs，並進行引用有效性檢查。

Graph 調整：增加「Wiki 來源映射檢查」節點放在「產生投影片」之前，降低後續回頭重寫整份簡報的成本。

這份紀錄明確區分：已完成的資料整理與靜態檢查、設計但未自動實作的迴圈。
